# Supabase 여행 데이터

TripBoogie의 모든 여행은 Supabase 프로젝트 `faekdclvcieuksoxsrtw`에 저장한다. 신규 기기 저장 모드는 제거했으며 이전 미동기화 localStorage 여행은 가져오기 전까지 원본을 보존한다. 로컬 미리보기와 배포 앱은 같은 Supabase를 사용하므로 같은 계정으로 로그인하면 같은 서버 여행을 연다.

## 저장 테이블

| 테이블 | 내용 |
|---|---|
| `profiles` | 이름·이메일·기준 통화·공휴일 국가·검색 언어·버전 |
| `trips` | 여행 정보·분류/여행지 설정·소유자·버전·전체 변경 번호 |
| `trip_members` | 여행별 소유자·편집자·열람자 |
| `trip_records` | 일정·장소·경비·체크리스트·예약, 작성자·항목 버전·삭제 표식 |
| `trip_overview_days` | 원본 일정과 독립된 날짜별 공유 요약·불러온 일정 ID·날짜별 버전 |
| `trip_invites` | 초대 토큰의 SHA-256 해시·권한·만료·취소 상태 |
| `trip_files` | 비공개 첨부 메타데이터·예약 연결·pending/ready/deleting 상태 |

모든 테이블에 RLS를 적용했다. 익명 테이블 접근과 로그인 사용자의 직접 INSERT/UPDATE/DELETE 권한은 없다. 로그인 사용자의 SELECT는 해당 여행 멤버십에 제한되며, 초대 목록은 소유자에게만 보인다. 표시용 사용자 메타데이터를 권한 판단에 사용하지 않는다.

브라우저의 Supabase 사용자 JWT를 앱 API가 `/auth/v1/user`에서 검증하고, 같은 JWT로 Supabase의 `tripboogie_api` RPC를 호출한다. 데이터베이스는 `auth.uid()`로 현재 사용자를 확인하고 멤버십·버전·수량·날짜·참조 관계를 다시 검사한다. 앱 서버도 사용자를 임의 지정하거나 관리자 키로 RLS를 우회하지 않는다.

공개 RPC는 SECURITY INVOKER다. 원자적인 여행 생성·초대 수락·멤버 관리와 쓰기 검사는 노출하지 않은 `tripboogie_private` 스키마의 함수가 담당한다. 이 함수는 내부에서 사용자를 확인하고 여행 행을 잠근 뒤 권한을 검사한다. 다른 private 함수의 직접 실행은 차단하고 모든 함수의 search_path를 고정했다. 이 private 스키마를 Data API의 exposed schemas에 추가하지 않는다.

## 권한과 동시 수정

| 작업 | 소유자 | 편집자 | 열람자 |
|---|---|---|---|
| 여행·항목 보기 | 가능 | 가능 | 가능 |
| 여행 정보·항목 수정 | 가능 | 가능 | 불가 |
| 한눈에 보기 요약표 수정 | 가능 | 가능 | 불가 |
| 자신의 체크 완료·함께 한 번 체크 | 가능 | 가능 | 가능 |
| 첨부 업로드·삭제 | 가능 | 가능 | 불가 |
| 초대 생성·목록·취소 | 가능 | 불가 | 불가 |
| 다른 멤버 제거 | 가능 | 불가 | 불가 |

각 변경은 하나의 Postgres 트랜잭션으로 처리한다. 같은 항목의 오래된 버전은 409로 거절한다. 삭제한 ID는 남겨 재연결한 클라이언트가 항목을 부활시키지 못하게 한다. 장소가 참조 중이면 삭제하지 않으며, 일정 날짜는 여행 기간 안에 있어야 한다. 한 여행의 기간은 기존 화면 제한과 같은 최대 365일이다.

멤버십 변경·수정은 같은 여행 행 잠금을 사용한다. 계정별 여행 수 제한은 생성·초대 수락 시 계정별 트랜잭션 잠금으로 함께 보호한다. 초대 링크는 친구 여러 명이 만료·취소 전 사용할 수 있고, 기존 멤버가 다시 수락해도 역할을 바꾸지 않는다. 멤버 제거는 현재 접근을 해제하며, 아직 유효한 초대 링크까지 취소하려면 초대도 따로 취소한다.

일정·예약 등 기존 화면은 온라인에서 약 8초 간격으로 갱신하며, 일정의 한눈에 보기를 열면 약 3초 간격으로 갱신한다. 기존 여행 레코드에는 실시간 푸시·오프라인 공동 편집 대기열을 제공하지 않는다. 브레인스토밍 문서는 아래 별도 저장·동기화 구조를 사용한다. 친구끼리 보는 여행의 경비는 모든 멤버에게 보이며, 경비 항목별 나만보기는 아직 구현하지 않았다.

## 환경 파일과 관리 연결

- `.env.local`: 로컬 Next.js 서버의 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`와 선택적인 지도 설정. 운영은 같은 이름을 Vercel 환경에 설정한다.
- `.env.management`: 이 프로젝트의 관리 스크립트만 사용하는 `TRIPBOOGIE_SUPABASE_PROJECT_REF`, `TRIPBOOGIE_SUPABASE_MANAGEMENT_TOKEN`.
- 관리 토큰은 런타임·브라우저·배포 아카이브에 전달하지 않는다. 전역 CLI 로그인과 기존 `0xseo` 플러그인 연결도 변경하지 않는다.
- 관리 스크립트는 프로젝트 ref를 고정하며 전역 환경이나 저장된 CLI 토큰을 사용하지 않는다.

```sh
node scripts/supabase-admin-check.mjs
node --test app/server/integration.test.mjs
npx tsc --noEmit
```

현재 초기 스키마는 이미 적용했다. `supabase/migrations/20261018054025_initial_tripboogie.sql`은 적용 이력과 같은 서버 버전을 사용한다. 같은 SQL을 다시 실행하지 않는다. 이후 변경은 `supabase migration new <name>`으로 새 파일을 만들고 검증한 뒤 `scripts/supabase-apply-migration.mjs`로 적용한다. 이 스크립트는 같은 이름의 재적용을 거절하고 서버의 실제 버전에 로컬 파일명을 맞춘다.

`supabase/config.toml`은 CLI가 만든 로컬 개발 설정이다. 기존 소셜 로그인 설정을 덮어쓰는 원격 config push 용도로 사용하지 않는다.

## 기존 데이터 이전

2026-10-18에 기존 로컬 D1의 여행 1건·소유자 1명을 Supabase로 이전했다. 제목·목적지·기간·통화·시간대·버전·변경 번호가 백업과 같은지 확인했다. 원본 D1은 삭제하지 않았다.

비공개 백업은 `.sites-runtime/backups/20261018T054214Z/`에 있으며 SQLite 스냅샷, JSON, 체크섬과 import receipt를 포함한다. 해당 디렉터리와 `.env.management`는 Git/배포에서 제외된다. 배포 D1은 전환 전 5개 테이블을 조회했을 때 모두 비어 있었으며 전환 후 다시 확인한다.

기존 `db/`와 `drizzle/`는 D1 이력과 복구 참고용이다. 현재 여행 API는 D1을 호출하지 않는다. D1 바인딩은 기존 데이터를 보존·조회하기 위해 당분간 유지한다. 새 여행 저장을 D1과 Supabase에 이중으로 쓰지 않는다.

## 검증 범위

- PGlite의 실제 Postgres에서 전체 마이그레이션·API 어댑터·RLS·권한·초대·버전 충돌·삭제 표식·날짜/장소 참조·저장 한도 검증.
- 실제 Supabase Postgres 17에서 기존 Auth 계정 두 개를 사용한 역할 검증을 트랜잭션으로 실행한 뒤 롤백. 실제 사용자 여행이나 로그인 설정을 테스트로 수정하지 않음.
- 보안 advisor에서 테이블·함수 관련 경고 없음. 기존 Auth의 유출 암호 차단 옵션 비활성화 경고 1건은 별도 설정 항목으로 남아 있음.
- PGlite는 단일 연결이다. 로컬 Promise 경합 검사는 버전 충돌 처리를 확인하며 다중 DB 연결의 잠금 동작을 측정한 결과가 아니다.
- 위 역할 검사는 JWT 검증을 흉내 낸 SQL 테스트다. 실제 브라우저 두 개의 로그인→초대→편집 종단 테스트를 대신하지 않는다. 사용자에게 기존 로그인 세션으로 새 여행 생성·새로고침·친구 초대 확인을 안내한다.

## Worker 전송 오류 수정 (2026-10-18)

Supabase 이전 뒤 로컬 로그인 사용자의 여행 목록이 503으로 실패했다. 데이터베이스에는 카카오 계정 소유의 여행 1개와 멤버십 1개가 보존되어 있었다. 원인은 저장소 HTTP 어댑터의 redirect: error였다. 실제 Wrangler/Workerd에서 이 옵션은 Supabase로 요청하기 전에 TypeError를 발생시켰다. Node 기반의 대체 HTTP 전송 테스트는 이 런타임 차이를 검증하지 못했다.

어댑터는 redirect: manual을 사용하고 3xx를 정상 응답으로 처리하지 않는다. 따라서 인증 헤더가 다른 주소로 전달되지 않는다. 예상하지 못한 저장소 오류는 작업 이름, 단계, HTTP 상태와 오류 코드만 서버에 기록하며 토큰, 본문, 여행 정보는 기록하지 않는다. 목록 조회 실패는 빈 목록 안내로 바꾸지 않고 지속적인 오류 안내와 재시도 버튼을 표시한다. 계정 변경 시 진행 중이던 이전 목록 요청은 무시한다.

검증: 실제 Worker에서 기존 옵션의 TypeError 재현, 실제 저장소 클래스에서 잘못된 테스트 JWT에 대한 Supabase의 401 응답 도달, Postgres 통합 검사 4개 통과, TypeScript 검사 통과. 실제 카카오 세션의 최종 조회 여부는 로컬 서버 요청 로그로 별도 확인한다.


## 2026-10-18 서버 저장·일정 확장

`20261018074309_server_storage_and_backup.sql` 적용. 비공개 `import_receipts`와 `map_rate_limits`는 RLS를 켜고 직접 테이블/보조 함수 접근을 차단한다. 기존 private dispatch만 인증·멤버십 검사 후 호출한다. 서버 가져오기(4 MiB), 소유자 여행 삭제(revision), 일정 일괄 편집(256 KiB), 장소+일정 원자적 생성, 계정별/전역 지도 요청 제한이 추가되었다. 일반 요청 한도는 64 KiB다.

기존 여행 원본을 비공개 백업한 뒤 적용했다. 실제 Supabase에서 적용 전·후 로그인 역할 워크플로를 롤백으로 검증했다. PGlite 통합 검사 10개도 통과했다. security advisor의 새 비공개 테이블 no-policy INFO는 의도한 직접 접근 금지다. 기존 Auth leaked-password-protection WARN과 미사용 인덱스 INFO는 별도 설정/사용량에 관한 사항이며 이 변경에서 인증 정책을 바꾸지 않았다. 두 브라우저의 실제 새 기능 전수 검증은 별도로 남는다.


## 상세 여행 작업 공간

`detailed_travel_workspace` 마이그레이션은 기존 레코드를 재작성하지 않고 필드와 예약/첨부 구조를 추가한다. 예전 경비는 원래 금액·통화를 유지하며 조회할 때 임의로 현재 환율을 적용하지 않는다. model=2 경비는 tripCurrency/baseCurrency/paidCurrency, 두 금액, 저장 환율·기준일, 결제자별 금액과 분담자 ID/표시 이름을 함께 보관한다. 결제자별 합계를 Postgres numeric으로 검증한다. 프로필 통화 변경은 기존 경비를 수정하지 않는다.

체크리스트의 created_by는 신규 INSERT 당시 auth.uid()가 소유하며, 완료 API는 자신의 ID에 대한 값만 바꾼다. 일반 수정의 checks 값은 무시하고 서버의 기존 완료 맵을 보존한다. 열람자는 콘텐츠를 편집할 수 없지만 체크리스트 참여는 가능하다. 이전 행의 작성자는 추정해서 채우지 않는다. 사용 중인 분류는 항목을 옮기기 전까지 삭제할 수 없다.

예약 연결 일정은 bookingId/bookingEvent/bookingDate/bookingOverrides를 서버에서 검증한다. 제목·장소·지속시간·분류 수정은 독립적으로 보존하고, 시간은 처음 생성할 때만 예약에서 가져온다. 날짜·메모는 예약과 공유한다. 복사 시 원래 예약의 소유권을 이어받지 않는다. 여행 전체 가져오기는 새 예약 ID로 참조를 재연결한다.

첨부파일은 `tripboogie-private` 비공개 버킷에 둔다. 준비 메타데이터 생성 → JWT로 Storage API 업로드 → 실제 오브젝트 크기 확인 → ready 순서다. 삭제는 deleting 표시 → Storage API 삭제 → 오브젝트가 없음을 확인한 뒤 메타데이터 제거 순서다. 실패하면 상태와 경로를 보존해 자료함에서 재시도한다. 여행 삭제는 첨부부터 처리하고 마지막 최신 revision으로 여행을 삭제하며, DB는 첨부가 남아 있는 여행 삭제를 거절한다. SQL로 storage.objects를 직접 삽입/삭제해서 실제 파일을 관리하지 않는다.

파일당 6 MiB, 여행당 200개/100 MiB이며 PDF·JPEG/PNG/WebP·DOCX/XLSX·TXT를 허용한다. 업서트/파일 교체는 지원하지 않고 새 경로를 발급한다. JSON 백업에는 예약과 파일 메타데이터가 포함되지만 바이너리는 자료함에서 따로 내려받아야 한다. 가져오기에서 친구 권한과 첨부 오브젝트를 복제하지 않는다.

검증에는 기존 Auth 계정의 SQL 역할만 사용하고 모두 롤백했다. 새로운 테스트 사용자를 만들거나 실제 사용자에게 메일을 보내지 않았다. 기존 Auth 유출 암호 차단 WARN과 비공개 내부 테이블 no-policy INFO는 이 변경으로 추가된 공개 접근 문제가 아니다. 실제 Storage HTTP 업로드/삭제 종단 확인은 아직 별도로 남아 있다.


## 도시·분담 금액·달력 변경

`cities_shares_and_calendar`는 프로필에 공휴일 국가 필드를 추가하고 기존 비공개 RPC의 도시/분담 금액 정규화를 확장한다. 기존 여행·경비 행을 재작성하거나 전체 사용자 데이터를 내려받지 않는다. 공휴일 국가를 별도 지정하지 않은 프로필은 조회 시 기준 통화의 대표 국가를 사용하며, EUR 등 대표 국가가 하나로 정해지지 않는 통화는 직접 선택한다.
